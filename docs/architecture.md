# Design-system book architecture

The separately installed workspace extension registers `vscode-design-system`, displayed as **Visual Studio Code Design System**. This package owns source adapters, view, controllers, runtime, CLI, and tests. The selected checkout owns the book definition, curation, and authored guidance outside the extension. The canvas and headless interface are direct entry points; no launcher skill is required.

## Content and view boundaries

The repository's [book.json](https://github.com/microsoft/vscode/blob/chryw/design-system-exploration/.github/design-system/book.json) identifies the book and its curated topics. Repository-owned page definitions bind source guidance and examples to logical visual blocks. Product code and code-local specifications remain authoritative; component and foundation prose live beside their owners, while cross-cutting guidance lives in `.github/design-system/guidance/`. [Authoring conventions](https://github.com/microsoft/vscode/blob/chryw/design-system-exploration/.github/design-system/authoring.md) define placement and naming.

The full book is the default experience. Ordinary sidebar navigation selects a topic, the runtime reads its dependencies just in time, and fixed renderers present the resulting projection. Canvas actions are optional navigation and inspection interfaces; the book does not depend on an agent requesting each article.

`runtime/` owns serving, lifecycle, revisions, state, and safe resource access. `adapters/vscode/` knows the selected checkout's source organization. `view/` owns presentation and interaction mechanics. The headless CLI uses the same source projections without requiring a visible canvas.

The package contains no book manifest, chapter data, or design guidance. `adapters/vscode/repository.mjs` reads a bounded, validated projection from `.github/design-system/` in the canonical selected checkout. Each runtime has its own catalog and metadata; an explicit root never falls back to the provider checkout's content. `/api/repository` supplies the browser's local presentation context before mounting any article. Portable snapshots embed the same projection. Installing this package separately must leave repository content usable without this viewer. There must be only one active registration for the stable canvas ID.

The lazy registered/contributed color-definition reader and saved-fixture source-tree synchronization belong to this runtime. Product motion tokens/controllers remain in their owning product files; the motion topic reads those saved sources directly.

The fixed modules use `.mjs` so Node and browsers run the same ESM without a compiler. Their narrowly scoped `code-no-new-javascript-files` lint exception documents this deliberate no-build requirement; repository lint configuration is unchanged. Other applicable lint rules still run.

## Topic contract

The checkout's `book.json` declares stable topic IDs, groups, titles, aliases, page references, logical renderer kinds, comparison support, and optional fixture support. `model/catalog.mjs` validates that metadata and creates an instance-local catalog without reading product sources. Renderer kinds resolve through an explicit registry rather than arbitrary executable module paths. Component IDs are `component-<controlId>`; old `section=components&controlId=...` URLs remain supported.

The shell requests `/api/catalog`, `/api/state`, and `/api/topic?id=...`. There is no aggregate `/api/system` endpoint or eager reader. Topic responses use a versioned envelope with canonical checkout identity, reader/template versions, dependency revision, source allowlist, coverage and separate capability readiness. Normal agent summaries are bounded and point to the full HTTP topic payload.

Authored documents are first-class content alongside these curated topics. [The document contract](documents.md) defines bounded source discovery, section composition, metadata, links/media, revisions, search, HTTP responses, and the equivalent CLI/canvas controls. The Documentation topic is one library, not a catalog entry per discovered file; adding an ordinary Markdown file within a configured scope requires no renderer change.

`model/view-state.mjs` owns field schemas, defaults, validation, and URL serialization for the live runtime, SDK actions, and portable viewer. A document's identity is its repository-relative source path within the bound checkout. Search and selected-document state share the existing durable per-instance lifecycle.

## Reader ownership

The component inventory explicitly selects reusable interaction/presentation contracts. [component-specs.mjs](../view/component-specs.mjs) presents toolkit evidence without publishing one topic per symbol; [qualification and granularity](https://github.com/microsoft/vscode/blob/chryw/design-system-exploration/.github/design-system/components.md) defines the boundary. Variants and structural parts normalize to their parent family, while toolkit-only compositions remain hidden archival references for old links. SDK/CLI listings and full-book navigation expose only the curated topics. An explicitly selected archive can remain readable without returning to navigation. Ready topics validate APIs against the actual owning source, including combined family APIs, and declare mapped fixture dependencies. Missing references stay TBD. Legacy overview IDs normalize to Button.

`adapters/vscode/readers.mjs` selects named lazy groups. Size registrations are parsed once per instance/revision, shared by Typography, Spacing, Shape, Size, Stroke, and lookup. Typography adds its native-family/baseline projection; Spacing doesn't load it. Theme scans, glyph catalogs, motion evidence, and component sources execute only for topics that need them. Selected component docs load only the owning component's files. Fixture discovery imports the preserved checkout-bound connector only when an actual preview requests it.

Source parsing, Git provenance, and fixture discovery live under `adapters/vscode/`, not `view/`. Shared data validation and derivation live under `model/`; presentation modules consume projections and have no filesystem or repository-data imports. Review archives preserve the same ownership split: viewer implementation in `book/`, checkout-owned metadata and source Markdown at their original relative paths under `repository/`.

Every group records files before reading them, including missing files. An unreadable source throws. Parsed results are shared across consumers; aborting one consumer doesn't cancel another consumer's shared parse. Projections are keyed by canonical instance root, dependency revision, reader version, and settings. There is no disk cache or cross-process broker.

Coverage remains source-defined, implementation-only, not-defined-in-covered-sources, or not-assessed, with explicit covered source paths. Viewer slots aren't product values. Existing fixed render functions remain responsible for visualization; never generate application code from a browsing request.

Colors additionally inventories literal/constant `registerColor` definitions and built-in extension color contributions through the lazy AST reader in `adapters/vscode/color-catalog.mjs`. It preserves definition locations independently of theme overrides, resolves supported defaults, and keeps computed/unset values explicit. The known-variable inventory is a cross-check, not a substitute for source definitions; unmatched and additional entries remain available in reader diagnostics. Typography/Spacing and the theme silhouette gallery do not trigger this registry scan.

Design tokens is a curated choice reference, not a registration or styling census. Its [qualification contract](https://github.com/microsoft/vscode/blob/chryw/design-system-exploration/.github/design-system/foundations.md) includes documented design scales, semantic color roles, declared motion parameters, the surface-shadow scale, and explicitly registered scoped layout parameters. It excludes glyph/file inventories, style-map fields, syntax taxonomies, structural geometry, and Figma specimens. It reuses the color resolver against only the semantic-role definitions; Tokens does not run the full color-registration or icon scans. Guidance-backed domains and compatibility aliases mount lazily, and contextual links lead to the complete color, icon, and motion references.

The Colors article presents property-and-purpose guidance. Its examples automatically connect the shared Component Explorer renderer for existing IconLabel, Button, InputBox, and Radio components when the article opens; the canvas owns no imitation control styling or separate fixture. `semanticColors.ts` registers usage-oriented foundations, while existing UI identifiers remain compatible aliases and preserve their theme/customization overrides. The single four-theme table initially shows these foundations, with an explicit option to include existing component colors. It uses the same token-name and CSS-copy helper as Design tokens. Definition coverage, source bookkeeping, per-value disclosures, and design-audit commentary remain in agent-facing data rather than the article. Its lazy `colorUsage` group validates curated source anchors and tracks fixture dependencies. Atlassian and Fluent inform the property/purpose distinction and semantic guidance without importing their palettes.

Article copy describes design roles, component behavior, and available interactions. Keep authoring rationale, implementation defenses, and claims about preview authenticity out of the reference. Preserve source links, API contracts, accessibility requirements, and actionable failure states.

The presentation doesn't render catalog-wide curation gaps, reservation reasons, migration observations, empty content slots, or missing-scale callouts. Those assessments remain available in reader data and inspection actions. Undocumented components show one concise availability sentence and their Figma specification link when present; they don't manufacture examples or APIs. Component preview connection/session diagnostics are not repeated in each article.

Articles follow a reader-first sequence: explain the decision, demonstrate it, then provide the full scale or technical reference. Typography leads with hierarchy and emphasis before the role and font reference; Shape leads with surface roles before the corner scale; Size and Stroke group examples before their values; Elevation puts usage and high-contrast guidance before the shadow scale. Spacing explains relationships and interval ownership before patterns and the product example, with the ramp last. Motion isolates properties and timing before applying them through intent-based recipes. Theming explains contrast before comparing all available themes, with the core themes first. Accessibility starts with keyboard behavior and names before announcements and integration details.

The shared article frame owns `--article-section-gap`, `--article-content-gap`, and `--article-measure`. Motion gives its title, introduction, outline, prose, and players one centered column in narrow articles; only an article wide enough for two examples expands that measure. The section/subsection/example typography uses the product heading ramp, with sequential HTML heading levels. Summaries introduce a decision without enumerating guidance repeated below. Paired examples align their players, while the widgets inside retain native proportions. Player frames contain only motion, controls, and necessary loading/error messages. Other topics retain their appropriate layouts and interactions.

Section navigation is owned by the shared article frame. Articles with at least four major sections get one On this page outline from actual rendered headings, using curated labels where available. Short articles don't repeat their headings as a miniature link menu. Renderers don't add competing outlines or links to absent sections. Selecting an anchor moves focus and scroll position and persists the anchor without remounting the article or its live examples. Guidance excerpts preserve heading nesting beneath the article title.

The full book follows the documentation site's chapter–article–outline hierarchy. At 1200px and wider, the outline occupies a sticky right rail beside the reading column, while the chapter sidebar remains on the left. At smaller widths and in focused or comparison views, the same outline flows above the article sections with wrapping links. Its current-section indicator follows reading position without rewriting the URL or remounting examples. Scroll listeners belong to the rendered topic lifetime. Inventories retain their full-width, internally scrolling layout.

Bodies are self-contained: avoid repeated definition links, bibliography trails, generic related-topic links, or Explore actions. The article header exposes its primary source and a compact Source documents menu. Composed guidance has one Read full specification link per contributing document, opening the full source in the Documentation library. Original document links remain usable within the reader. Component Figma specifications and live examples retain their existing purpose-specific actions.

Copy actions are labeled buttons with local Copied or Copy failed feedback and the existing screen-reader announcement. Type-role and weight specimen labels are plain text, not disguised copy links. The token table keeps token, value, and purpose; domain guidance is inline without extra source links. At narrow widths, rows stack while retaining table semantics. Theme illustrations are comparisons, not ineffective Use theme actions.

## Scope and browser lifecycle

`replace`, `add`, and `all` operate on validated IDs. `all` is the default and expands discoverability without executing readers. Focused scopes remain available for explicitly requested standalone articles; `add` appends an article without replacing existing DOM. `compare` requires exactly two selected topics and uses two columns only at 1100px or wider; smaller panels stack them. Ordinary topic selection belongs to the book navigation; specialized scope changes remain canvas actions.

Only `all` mounts the reusable [book-navigation template](../view/book-navigation.mjs) and its [stylesheet](../view/book-navigation.css). It accepts flat `{ id, title, group, subgroup?, href }` items, an active ID, and a navigation callback; it imports no topic definitions. At 760px and wider, a persistent sidebar sits beside the article with a Find a topic field, collapsible metadata groups, and an independently scrolling link list. At narrower widths, Browse topics opens the same navigation as a native, nonmodal popover drawer without displacing the article. Its Close action, Escape, and native light dismissal close the drawer; opening it focuses the filter, and Escape restores focus to Browse topics. Resizing keeps focus on a visible navigation control.

The topic filter matches titles, aliases, and supplied group labels locally, opens matching groups, announces result counts, and shows an explicit empty state. Arrow Down moves from the filter to the first visible result. Topic filtering never reads sources or starts fixtures; document full-text search belongs to the Documentation library. Selection clears the filter, closes the narrow drawer, and moves focus to the article. The active group opens and its link is revealed within the sidebar's own scroll region. URL-only updates retain link and search-field identity, disclosure state, and scroll position; modified link clicks retain ordinary browser behavior. The template supports explicit subgroups but doesn't invent component families. Previous and Next links remain below the article. Focused requests remove book navigation entirely. Ready component articles retain local section anchors, not overview or scope controls.

The canvas header owns one **Refresh** action, including in comparisons. Checkout diagnostics are collapsed beneath the reference name, and Previous and Next links sit after the article so navigation doesn't displace its heading. Refresh rereads all visible topics, invalidates the shared fixture catalog once, and remounts their content while retaining view settings, filters, and selected fixture variants. Batch source reads run in order so overlapping dependencies cannot invalidate an in-flight sibling read. Live examples in every rendered article connect automatically, including Colors, Spacing, and Motion; there are no per-example Load actions. Full-book navigation still loads only the active article, not every topic's fixtures. Fixture failures, readiness timeouts, and missing variants explain the next step inline; they don't add separate reconnect, reload, or reset buttons.

Live previews reuse Component Explorer's embedded hot updates, including changes to imported product code, styles, and tokens. Only fixture-definition edits invalidate the catalog and wait for a new fixture source tree; imported implementation changes don't imply a catalog change. An initial discovery failure, render failure, or readiness timeout triggers one automatic rediscovery and reload while retaining the selected variant. Healthy previews check the cached renderer's loopback HTTP endpoint every 15 seconds and when the page becomes visible; checks share an in-flight health request and don't start MCP discovery. A disconnected renderer invalidates the cache, then the preview rediscovers its current local address. Hidden documents and inactive articles stop health checks, and disposal cancels timers and listeners. Recovery stops with an explicit Refresh fallback if its single attempt fails; it doesn't restart or terminate the shared daemon. A new successful ready message restores the recovery allowance, and a real online event can retry an unavailable preview.

Fixture variants and writing directions use labeled native radio groups, so choices remain visible and keyboard-operable. Switching fixture variants reuses the frame and leaves keyboard focus on the choice. A missing saved variant keeps the available choices visible rather than requiring URL repair. Component articles lead with a preview, followed by usage, accessibility, and API sections with consistent heading levels. The shared compact preview presentation omits extra metadata without changing fixture behavior.

Spacing leads with relationships and concise pattern guidance, followed by interval ownership, narrow-layout guidance, and one complete copyable token ramp. Its automatically connected Component Explorer example reuses the existing Buttons fixture, sharing the normal preview renderer with diagnostic details omitted. It retains its selected theme through Refresh. Its lazy reader retains curated Automations and Agent settings evidence internally and declares the existing button fixture and implementation as dependencies. Source bookkeeping and coverage judgments are not article content, and the numeric ramp remains the shared primitive rather than introducing per-feature spacing aliases.

Book navigation and pagination retain full-book scope. Named topic requests remain standalone articles. Neither path adds custom back/forward controls.

The SDK embeds the stable instance root URL, not a scope snapshot. Rehydrating that frame reads the current server state instead of replaying the initial selection. Explicit topic deep links still apply their requested scope. Scope/view events replace the browser's current URL, and every event-stream connection receives the latest state so delayed connections and reconnects cannot miss an earlier action. After reconnecting, the shell rereads visible articles to recover source updates missed during the interruption, then removes its separate connection notice. Back-forward cache restoration also resynchronizes state and visible data without creating another event stream.

The shell keeps one mounted pane per visited selected topic. Adding another topic doesn't replace existing DOM. Only changed topic settings or removal dispose a pane; inactive selected panes remain hidden. Scope removes watches for inactive topics. Query changes retain the search field. Existing render-generation cancellation prevents stale reads/render completions from replacing current content.

Saved changes invalidate matching groups, not all topics. Parent-directory watchers survive atomic saves; expected missing sources watch the nearest existing parent. Reused watchers resolve the current group's file set rather than retaining the original subscription, and filename-less notifications check the relevant directory's signatures. Theme-directory discovery is active only with color/theming subscriptions. Small revision events identify affected topics and changed paths; the browser rereads those projections. Topic reads retry one racing source revision, but don't retry invalid registrations or other permanent read failures. Watch errors remain explicit. Code/template edits may require restarting the owned runtime; source-data edits don't.

## Trust and stop behavior

The runtime is immutably bound to the canonical root chosen by the workspace adapter or explicit CLI argument. HTTP can't change roots. Assets and source links are allowlisted; repository-relative source paths reject traversal and symlink escape. Host/Origin checks and bounded JSON apply to mutations. Markdown isn't executed and source HTML is escaped.

The fixed `/codicon.ttf` asset is read from the selected checkout's installed Codicon dependency, including an existing linked dependency directory. It isn't a user-selected source path; this exception doesn't relax containment for source links. The glyph reader also checks that dependency's fixed CSS mapping by code point, preserving aliases and marking source registrations absent from the installed package as “Not installed.” Dependency asset changes require a topic refresh or runtime reload; they aren't watched as checkout sources. Iconography waits for the font face to load before committing glyph previews, so a failed font request becomes a topic problem instead of a successful gallery of fallback boxes.

One canvas instance owns its server, caches, request cancellation and watchers. SDK close or `stop_explorer` disposes them idempotently; presentation hiding isn't treated as close. Validated scope and per-topic view changes are saved before being published to the page, so a failed save cannot look like a successful persistent action.

Private view state lives under `extension-data/vscode-design-system/` in the resolved Copilot home. Its identity combines the canonical checkout, book, and stable canvas instance; it is not keyed solely by a panel handle. Separate canvases cannot overwrite one another's active chapter, filters, or preview selections. Writes read the latest record, preserve unrelated topic preferences within that view, and use a lock plus a uniquely named temporary file and atomic rename. Unsupported or corrupt records fail explicitly rather than resetting preferences. Reopening the same instance after a provider restart restores this state; source projections themselves remain regenerable in-memory caches.

A shared Component Explorer daemon is not owned by an arbitrary canvas; closing discovery clients must not terminate it.

The fixture connector keeps its third-argument `AbortSignal` contract. Its optional fourth argument is the last source-tree ID invalidated by a saved fixture catalog edit. If the daemon still reports that tree, discovery waits for the update, rereads sessions, and rejects a stale result rather than reporting a successful refresh. The SDK's five-second no-change response is not a failed build: discovery can continue that long-poll for at most 30 seconds or six responses, without restarting discovery or dropping cancellation. Saved `.fixture.ts` changes require a new renderer tree; imported implementation and stylesheet changes use Component Explorer's live updates, and documentation-only edits don't wait for an unrelated build. Catalog discovery is single-flight, and a superseded generation cannot become the cached result. Automatic startup remains checkout-local and idempotent.

Motion has four article sections: Principles, Foundations, Best practices, and Accessibility. [Its page definition](https://github.com/microsoft/vscode/blob/chryw/design-system-exploration/.github/design-system/pages/motion.json) composes heading references from the product's [Motion specification](../../../../src/vs/platform/theme/common/motion/MOTION.md) with allowlisted visual blocks and fixture bindings. The source adapter reads both files as tracked dependencies, validates referenced headings, examples, token IDs, and CSS variables, and returns the actual authored Markdown. The view does not keep a parallel copy of that guidance.

Foundations contains Duration, Easing, and Properties; Best practices contains Transitions, Feedback, Progress, and Expression. Generic endpoint and zero-delay tokens are absent: recipes carry literal geometry or intentional component parameters. The nine shared easing curves use short VS Code names and the verified Fluent values. Four family players expose their applicable variants without duplicating a long token list.

Duration groups immediate, short, and visible transitions by source-backed ranges. Native List, Button/Menu, view-choice, and notification examples show the corresponding feedback, entrance, replacement, and awareness. The List scopes its feedback transition without changing product defaults. Menu keyboard navigation, Escape, and focus return remain intact. Layout examples use one reversible control, preserve the left or top origin, and move following content when a section is inserted. Color runs the shared listening rim with a pausable clock; reduced motion stops its drawing loop. Scale uses a blue square for subtle card emphasis. Easing and activity variants use one-click pivots. Numeric references remain in Design tokens; the Motion article omits recipe/CSS disclosures and Component Explorer links.

Motion reads base size/type tokens, source workbench font families, the shared fixture's default palettes, the product button stylesheet, and the Codicons it needs. It doesn't load the theme gallery. The palette adapter checks its mapping against fixture defaults. Static `transparent()` colors resolve referenced theme colors or built-in Color constants, including the actual widget shadow. Canvas player controls use native buttons with product CSS; product examples instantiate the real widgets. Curve changes cancel the previous diagram lifetime without remounting product frames; layout input retargets the current CSS transition.

All players have one canvas-owned icon button for Play, Pause, and Reset. Finite runs keep their ending state until Reset; no automatic return, dismissal, or replay is scheduled. Reset cancels outstanding work and restores the baseline without playback. Interactive controls remain usable directly. Finite fixture completion waits for the actual animations to settle; stale sequence messages are ignored. Looping indicators start on a representative paused frame and resume rather than rebuilding the same working state. Reduced motion has one local demonstration under Offer reduced motion; matrix and ring share an activity example. The iframe renderer validates message source and origin and preserves frame identity across input changes. Offscreen viewers pause without substituting reduced motion. The fixture clock preserves reporting delays and animation time; the illustrated activity uses the existing component clock and scheduler. No global browser clock is patched.

The renderer uses Component Explorer's `component-explorer:embedded-input` message, and fixtures observe schema input through `watchInput`; changing a motion choice doesn't reload the iframe or remount the component. Motion previews load near the viewport and use the embedded resize message's width and height rather than a fixed oversized frame. Ready captions are omitted from Motion viewer chrome; loading and failure states remain visible. Health polling pauses offscreen. Saved-source invalidation covers the canonical documentation, fixtures, and owning product styles. The article's single source action links to the canonical system.

## Validation

```sh
node /path/to/vscode-design-system/scripts/test.mjs --root /path/to/checkout
node --test /path/to/vscode-design-system/tests/presentation.browser.mjs
node --test /path/to/vscode-design-system/tests/colors.browser.mjs
node /path/to/vscode-design-system/scripts/book.mjs list
node /path/to/vscode-design-system/scripts/book.mjs validate --topics typography,spacing --compare
```

Check reader counts and downloaded modules independently of timing. Measure five warm local opens, refresh after a saved edit, payload bytes, and source parse counts. Keep fixture cold timing separate. Browser-only validation doesn't establish SDK canvas registration/actions. When changed adapter/runtime modules require a reload, retain task instance handles and scope, call `extensions_reload`, rediscover capabilities, and verify the same reopened canvas against the canonical checkout. Routine activation doesn't require an extra confirmation step. Don't restart unrelated services or bypass host-enforced permissions.

The presentation test uses the repository's existing Playwright installation and prepared Chromium. It checks focused/added/compared/book scopes, lazy reads, native keyboard behavior, focus handoff, DOM identity, reduced motion, and overflow at 320, 390, 500, 800, and 1440px. It closes its own browser and runtime and doesn't start Component Explorer.
